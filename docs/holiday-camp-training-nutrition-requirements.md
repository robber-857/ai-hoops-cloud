# 假期班首版：训练、三餐营养与个人中心需求

更新：2026-09-27。状态：需求整理完成；新功能尚未实施或验收。

执行入口：[开发交接](./holiday-camp-development-handoff-2026-09-27.md)。排期及验收：[开发计划](./holiday-camp-development-plan.md)。营养口径：[营养与 AFCD 规范](./holiday-camp-nutrition-spec.md)。UI：[个人中心方案](./personal-center-development-plan.md)。

## 1. 用户已确认的范围

- 在现有 AI Hoops 系统内开发；学员为 4–18 岁，家长直接代管球员账号，不建独立家长账号。
- 手机号或邮箱至少提供一个；不扩展同一家长多孩子管理。现有手机号必填约束需核对，支持邮箱单独注册需前后端和迁移一致。
- 假期班首版同时包含：个人中心桌面/手机改版、训练计划、教练课次记录、个人课后报告、全天三餐营养建议、独立菜谱页面及基础内容维护。
- 周期体测、体测批量导入、体测视频成长档案暂不做。
- 不记录实际饮食，不做饮食打卡、实际摄入追踪或实际热量缺口。
- 教练是训练记录主要输入者：记录班级运动项目、实际时长，并记录个人缺席、提前离场和部分参与情况。
- 课后报告在软件内生成，球员账号查看；不依赖邮件交付。
- 饮食建议明确到早餐、午餐、晚餐的碳水、蛋白质和脂肪克数/参考范围。
- 菜谱是独立页面，用户能浏览每道菜、食材和营养成分及含量；采用 AFCD 食品营养数据。
- 个人中心拆分历史记录、任务提交、趋势等独立页面。桌面顶部保留 Shooting / Dribbling / Training，个人中心在右上角；桌面左侧页面导航、右侧内容。
- 手机右上角个人中心与菜单，菜单包含桌面页面导航。已接受的设计方向为顶栏下方一行 Shooting / Dribbling / Training；详见 UI 方案。

## 2. 业务流程

教练制定并发布计划 → 球员查看 → 教练从计划创建课次 → 更新实际项目、时长和参与名单 → 确认发布 → 为参训球员生成课后报告 → 汇总当天已记录课程，生成同一天的三餐建议 → 用户按需浏览菜谱。

计划和实际记录分开保存。计划时长不代表实际参与时长，动作次数不直接等于精确热量。全班共享课次项目，每名球员保存个人参与覆盖项。缺席者保留缺席记录，不生成该课运动消耗报告；未确认状态不能默认为全勤。

## 3. 角色职责与报告

| 角色 | 主要操作 |
| --- | --- |
| Admin/内容维护人员 | 维护食品映射、菜谱、规则版本和基础资料；监督发布 |
| Coach | 仅管理授权班级；制定计划、记录课程和个人差异、预览并发布 |
| 球员账号（含家长代管） | 查看自己的计划、任务、报告、趋势和饮食建议；浏览菜谱 |

课后报告包括：课次/班级/日期、实际训练内容与参与时长、使用的身体资料及测量日期、运动消耗估算、当天三餐营养参考、来源和估算说明。它不是一次新的体测，不声称测得当天身体状态。

同日多课共享一个当天营养建议入口；修订课程后生成建议修订版本，避免用户把多份全天建议相加。晚上生成的全天参考不代表晚餐还需补吃全天量。

## 4. 建议采用的实现边界

- 首版训练目标使用“基础体能、动作与协调、篮球专项表现、综合发展”，作为教练训练重点，不做增肌/减脂热量开关。名称为当前设计默认值，可调整文案。
- 先完成结构化表单，再接文字/语音转写及 AI 整理；AI 输出需教练确认，不自动编造项目、时长、参与名单或营养数字。语音首版优先级和服务商未最终确定，不能静默删减，也不能成为手动录入的依赖。
- 训练计划支持班级分配及个人调整、日期、动作、组次/次数/时长、说明，可关联已有评分模板；普通篮球项目不要求必须存在视频分析模板。
- 新课次、参与记录、营养报告独立建模；不改变旧视频分析 session、评分 report、任务提交及增长统计的含义。
- 发布保存输入与规则快照，重复发布/网络重试不重复创建报告或通知。已发布内容更正留修订记录。
- 菜谱首版由机构维护，不做用户上传饮食照片识别，不做自动处方或自动长期计划。

## 5. 尚需落实的产品/内容决策

1. 4–18 岁各年龄适用的能量估算、运动估算、三大营养素目标及三餐分配规则；由谁审核和何时交付。
2. 首批菜谱及食物条目清单、图片和做法来源；数据许可与署名方式须在导入时核对。
3. 语音输入是否为假期班首版硬性门槛；服务商、语言和音频保留策略。

以上未知项只阻塞依赖它们的实现/发布，不阻塞导航拆分、班级计划和手动课次记录。
