## 2. 技术结构建议（尚未建表或批准具体表名）

复用 users、camp_classes、class_members、身份验证、Coach 班级授权和现有通知设施。

新增业务实体候选：身体测量记录、训练计划及项目、班级课次及实际项目、个人参与记录、课后报告快照/修订、每日营养建议、食品源版本/营养值、菜谱及食材/发布版本。

不要把新班级课次塞入旧 `training_sessions` 视频分析会话，也不要把饮食报告塞入 `analysis_reports` 导致旧评分统计变化。任务仍可关联现有动作评估报告；新计划完成度不能直接复用分数任务达标逻辑。

推荐服务边界：计划/课次业务、个人报告发布、营养计算、食品菜谱；按现有 FastAPI router → schema → service → model 分层。前端采用独立 Next.js 页面和服务客户端，敏感计算/授权放后端。精确接口和表名在实施批次内确定。

需要新增 Alembic migration；先在测试 PostgreSQL 验证。训练五模板旧文档的“不需要 migration”仅适用于当时模板同步，不适用于本需求。

## 3. 关键业务约束

- Coach 仅访问 active 授权班级，Student 只访问自己；菜谱全系统可浏览不等于个人报告公开。
- 发布时锁定身体资料、训练输入、规则与来源版本；改资料/规则不重算旧报告。
- 发布请求幂等，按课次/球员/修订保证唯一；部分失败可追踪重试，不重复通知，不静默漏人。
- 课次和每日建议按明确机构时区归日；同日多课和课次修订触发正确汇总。
- AI 整理只产生待确认输入；缺失字段、未知运动映射不能编造。
- 保留旧历史报告 URL、任务提交/重试/刷新及通知已读行为；新课后报告不增加旧评分统计。

## 4. UI 拆分建议路由

`/me` 概览；`/me/plans` 训练计划；`/me/tasks` 训练任务；`/me/class-reports` 课后报告；`/me/reports` 原动作评估记录；`/me/trends` 趋势；`/me/nutrition` 三餐建议；`/me/messages` 消息；`/me/profile` 个人资料。

菜谱独立为 `/recipes`、`/recipes/[id]`，个人中心侧栏和菜单均有入口。菜谱是否允许未登录浏览尚未决定，首版默认遵守现有认证边界，不自动开放私有内容。

路径是实施建议；开发时先核对实际目录，不因后端 `/me/tasks` 已存在就误认为前端已有该页面。详情页路径在各批次确定。

## 5. 验收与发布

- 前端：`web` 目录下 `npm.cmd test`、`npx.cmd tsc --noEmit`、`npm.cmd run lint`、`npm.cmd run build`；针对变更选取有意义测试。
- 后端：采用仓库 unittest 组织方式，运行相关服务/API 回归；旧记录指出虚拟环境解释器路径曾失效，先验证当前 Python，不盲用旧 workaround。
- 数据库：测试 PostgreSQL 的迁移、回退/前滚策略、实际保存读取、事务与并发重试验证；SQLite 单测不能替代。
- 浏览器：360/390px 手机、768px 平板、1280/1440px 桌面；菜单开关/键盘焦点、横向溢出、任务提交、筛选、长内容、空态/加载/错误态。
- 合成班级：至少覆盖全勤、缺席、提前离场、部分项目、未确认、缺资料、同日多课和重复发布。
- 集成：教练发布计划 → 记录参与 → 发布报告 → 球员登录查看 → 刷新/重新登录读取 → 修订 → 确认每日建议与历史一致。
- 旧动作分析：保留 Shooting/Dribbling 规则及历史快照；关联 Training 模板的真实视频验收仍按其专项文档执行，不能继承“已通过”的假定。
- 发布：核对实际 Vercel/Render/数据库环境与部署分支，先兼容迁移/后端再切前端；准备模块开关和恢复方案。旧 deployment 文档的固定 merge 顺序不是本次发布授权。

每批进度必须分开记录代码、自动化测试、数据库、浏览器、教练 UAT、部署状态，并附日期/版本/环境。健康检查和自动化测试不代表教练实用验收。
